# Операции: Agent, очередь, кэши и подготовка весов

## Предварительные условия

Нужны установленные CY и совместимые зависимости. Для экспериментов настройте
ClearML и хранилище; для ClearML Agent подготовьте его собственное окружение.
Очередь — отдельный пакет `cy-queue`, установленный в то же Python-окружение.
Документация CY использует существующий интерфейс очереди и не вводит её схемы
или plugin API. Сохраните чужие процессы, настройки и данные.

## Пример

### Подготовить pretrained-веса до отключения сети

```bash
cy-download-weights
```

Команда проверяет и готовит поддерживаемые детекторные YOLO-веса, RF-DETR,
подходящие backbone Faster R-CNN/FCOS и DEIMv2 small/medium с закреплёнными
исходниками. DEIMv2 large/xlarge и `dinov3_small` исключены из массовой подготовки;
их явный выбор сохраняет отдельные требования к доступу и локальным файлам.
Штатные веса помещаются в native-кэши библиотек, DEIM — под `CY_HOME`.
Конфигурация SDK не переписывается.

Сначала используются проверенные native-кэши, затем закреплённый релиз весов
`weights-*` в `BuckanovNikita/clearml-yolo`, затем исходные серверы моделей.
Архивы и файлы проверяются по размеру и SHA-256; для Hugging Face восстанавливаются
также конфигурация и метаданные snapshot. Ошибка зеркала выводит предупреждение
и сохраняет обычную попытку загрузки из upstream.

Релизы весов независимы от версий CY: новый релиз программы повторно использует
прежние архивы. Лицензии моделей сохраняются; DEIMv2 находится в отдельном архиве
для некоммерческого использования. Полный перечень источников и условий приложен
к архивам.

Ненулевой код означает неполную подготовку. Повтор команды повторяет недостающие
загрузки, сохраняя проверенные файлы. При выполнении полного `cy` автоматическая
попытка каталога происходит один раз для его расположений кэшей; частичные ошибки
дают предупреждение, а затем продолжается обычное разрешение выбранной модели.
`cy-train`, справка, config preview и queue submission массовую подготовку не запускают.

### Настроить proxy и повторить неудачную загрузку

Задайте сеть и окружение до нового запуска CY. Для полных архивов проекта `GHR`
указывает на Generic remote Artifactory с upstream `https://github.com`:

```bash
export GHR="https://artifactory.example/artifactory/github-releases"
```

Замените домен и ключ своими значениями. Весь путь
`owner/repo/releases/download/tag/file.tar` сохраняется под этим корнем; не задавайте
URL отдельного файла или GitHub API. Для аутентификации `GH`/`GHR` подготовьте
закрытую запись `.netrc` для реального хоста Artifactory; права файла — только
владельцу (`chmod 600 ~/.netrc`). `HF_TOKEN` не служит паролем для этих загрузок.

`GH=https://artifactory.example/artifactory/github-vcs` необязателен: он нужен для
резервной загрузки исходников DEIM, если полный архив проекта через `GHR` их не дал.
Из него получается
`https://artifactory.example/artifactory/api/vcs/downloadCommit/github-vcs/owner/repo/commit?ext=tar.gz`,
а не Git clone URL. Имя переменной — `GH`, не `CH`.

Если нужен отдельный HF fallback, задайте
`HF_ENDPOINT=https://artifactory.example/artifactory/api/huggingfaceml/hf-remote`.
Токен для этого endpoint загружайте через защищённое хранилище или штатный закрытый
файл токена SDK; не печатайте его и не добавляйте в YAML/журналы. Он относится только
к HF и не пересылается в посторонние upstream-запросы. Для корпоративного CA задайте
`SSL_CERT_FILE` и/или `REQUESTS_CA_BUNDLE` с настоящим путём к CA bundle, сохраняя
проверку TLS. После настройки начните новый процесс:

```bash
cy-download-weights
```

401 указывает на аутентификацию, 403 — права или политику доступа. При 404 проверьте
корень, ключ репозитория, исходный путь и доступность upstream. Ошибка размера,
SHA-256 или формата требует исправить ответ proxy/cache и повторить, не отключая
проверки и не удаляя валидные файлы. Явная команда повторяет попытку даже после
завершённой автоматической попытки с частичными ошибками.

Протокольные фикстуры подтверждают клиентскую логику URL, авторизации и fallback;
они не подтверждают доступность, права или кэш живого Artifactory. Для проверки
клиентской логики обращаться к живому стенду не требуется.

Для ручного восстановления разместите **указанные в диагностике** файлы по точным
путям, затем повторите; не угадывайте имена. Явные пути
[model.source_dir](/#field=model.source_dir),
[model.train.weights](/#field=model.train.weights) и
[ultralytics.model](/#field=ultralytics.model) остаются авторитетными.

### Повторить задачу через ClearML Agent

Проверьте завершённый запуск: сохранены `Configuration / run`, код/окружение,
доступный ground truth и веса. Клонируйте задачу через штатный интерфейс ClearML,
назначьте ей Agent queue и запускайте Agent в подготовленном окружении.
CY читает `run` до проверки обязательных входов/выбора backend и присоединяется
к той же задаче, даже если Agent не повторяет исходные CLI-аргументы.

Для явного изменения Configuration Object в своём ClearML-клиенте передавайте
полный JSON, например `json.dumps(full_run_config, ensure_ascii=False)`;
не отправляйте только изменённый фрагмент вместо полного документа. Сохранённые
`model_assets` и snapshots аугментаций описывают разрешённые ресурсы отдельно от
редактируемого исходного ввода.

Отсутствующий `run` допускает полный явный набор аргументов; пустой или некорректный
`run` — ошибка. Устройства Agent видны в логическом пространстве его
`CUDA_VISIBLE_DEVICES`; локальная очередь CY в таком запуске не участвует.
Зависимости устанавливает окружение Agent, а не preview или model resolver.

### Настроить и использовать отдельную очередь

После установки CY установите совместимый источник очереди в то же окружение:

```bash
uv pip install --python .venv/bin/python -e . -e ../cy-queue
uv pip check --python .venv/bin/python
cy-queue --help
```

Эти команды предполагают реальные checkouts CY и cy-queue, а не наличие пакетов
на PyPI. Перед обновлением работающих участников следуйте согласованной процедуре
drain/upgrade; смена установленного кода может потребовать повторной отправки
ожидающих задач.

Пользовательский TOML расположен в `$XDG_CONFIG_HOME/clearml-yolo/queue.toml`
или `~/.config/clearml-yolo/queue.toml`. Все поля обязательны. Пути ниже — пример;
используйте подготовленные оператором доступные абсолютные каталоги:

```toml
[queue]
name = "Team training"
root = "/srv/clearml-yolo/queue"
coordination_root = "/var/lib/clearml-yolo/coordination"
```

Абсолютный `CY_QUEUE_CONFIG` может выбрать общий файл. `cy-queue config --json`
показывает фактический источник настроек без создания директорий/задач. Файл не
создаётся автоматически. NFS требует согласованных UID и поддерживаемых условий
host locking; локальная проверка не доказывает двухпользовательскую или двуххостовую
корректность.

Сначала заполните экспортированный training YAML: ground truth, модель, ClearML
project/task/tags. Уберите явные native GPU overrides из queued-конфигурации.

```bash
cy-init-config train-config --command cy-train
cy-queue config --json
cy-queue submit --command train --gpus 1 -- --config-dir train-config --config-name cy-train
cy-queue worker
```

`submit` сохраняет неизменяемый снимок, worker выполняет его в отдельном процессе.
До старта нет экспериментальной задачи ClearML. В другом терминале:

```bash
cy-queue list --json
cy-queue cancel job-17
cy-queue recover job-17
```

Замените `job-17` реальным номером. `cancel` запрашивает отмену принадлежащего вам
запуска; `recover` предназначен для восстановления после нештатного завершения и
сохраняет проверки владельца/остаточных процессов. Не используйте его как способ
обойти занятую GPU. Для завершённых задач:

```bash
cy-queue archive job-17
cy-queue list --archived
cy-queue restore job-17
```

Архивирование меняет видимость, а не удаляет результаты. `cy-queue tui` открывает
терминальный интерфейс. Для очереди pipeline опустите `--command train`; для
перебора передайте `-m` после `--`, как при прямом Hydra запуске.

Очередь выбирает GPU, а не исправляет недостаток памяти модели. Автоматический
допуск требует используемой памяти строго меньше 2 GiB и отсутствия reservation/hold.
После обучения освобождаются дополнительные GPU; первая остаётся до завершения
pipeline/потомков. Без подтверждённого training-finished удерживается вся allocation.
Операторские `cy-queue gpu list/disable/enable/free/release` используют физические
индексы `nvidia-smi`; обычные submission-индексы — логические CUDA-visible.
`gpu free INDEX` очищает reservation/hold, но не завершает работающие процессы.

### Обслужить кэш без изменения содержимого

Приостановите запись в **свой** выбранный кэш и просмотрите кандидатов:

```bash
cy-dedup --dry-run
cy-dedup
```

По умолчанию это `$CY_HOME/.cache`; можно передать каталог позиционным аргументом.
На поддерживаемой Linux reflink-файловой системе одинаковые изображения разделят
блоки с copy-on-write, сохранив пути и байты. Это не удаление устаревшего dataset
cache и не подтверждение неизменности исходных изображений. Изменение байтов
изображения по тому же пути требует явного idle-обслуживания соответствующего
dataset cache; cache hit не проверяет image mtime/contents заново.

## Ожидаемый результат

Подготовка весов печатает cache destinations и результаты каждого asset. Agent
восстанавливает backend и полные входы из сохранённой задачи. Queue submission
возвращает job reference, worker меняет её состояние и запускает эксперимент.
Dedup показывает scanned/duplicates/reflinked/skipped/failures и код завершения.

## Частые ошибки

- Команда отсутствует: проверьте установленную версию и источник Python-окружения.
- Queue config отсутствует: заполните TOML, а не добавляйте устаревшие `queue.*`
  или `autogpu.*` ключи Hydra.
- Job ожидает GPU: проверьте readable reason, reservation/hold и память; preview
  не проверяет admission. `--gpus 0` не означает CPU очередь и не поддерживается.
- Agent выбрал другое устройство: проверьте его CUDA visibility и полный `run`.
- После обновления job несовместим: сохраните старую запись и отправьте новый снимок.
- Неполная подготовка весов: используйте диагностику точных путей и повторите команду.

## Проверка

Проверьте коды завершения, native cache discovery и реальную загрузку выбранных
весов без сети. Для replay сравните `run`, выбранный backend, model assets и
артефакты завершённой задачи. Для queue проверьте состояние своей job, журналы
worker, создание одной задачи и освобождение собственных ресурсов после выхода.
Повторный запуск dedup dry-run должен сохранять содержимое и имена файлов.
Ни один из этих результатов не следует из успешного предпросмотра конфигурации.
