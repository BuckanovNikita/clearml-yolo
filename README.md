# clearml-yolo

Набор переиспользуемых hydra-zen приложений: обучение YOLO с DDP и ClearML, инференс,
подсчёт метрик по всем сплитам через [digital-metrics](https://github.com/Wasilkas/digital-metrics)
и сравнение с предыдущей моделью через [report-generator](https://github.com/Wasilkas/report-generator).

## Установка

```bash
uv sync
```

Перед первым запуском нужно настроить ClearML (файла `~/clearml.conf` в системе может не быть):

```bash
uv run clearml-init
```

Либо через переменные окружения: `CLEARML_API_HOST`, `CLEARML_WEB_HOST`,
`CLEARML_FILES_HOST`, `CLEARML_API_ACCESS_KEY`, `CLEARML_API_SECRET_KEY`.

## Приложения

Каждый этап запускается самостоятельно, либо все сразу через `cy`.

| Команда | Что делает |
|---|---|
| `cy-ground-truth` | разметка из `data.yaml` в CSV, который читают все следующие этапы |
| `cy-train` | обучение YOLO (DDP, авто-выбор GPU) |
| `cy-predict` | инференс, CSV предсказаний в схеме digital-metrics |
| `cy-metrics` | метрики по каждому сплиту, дашборды в xlsx |
| `cy-report` | сравнение с базовой моделью, dev и business отчёты |
| `cy-compare` | статистическое сравнение двух моделей по их задачам ClearML |
| `cy` | весь конвейер одним экспериментом ClearML |
| `cy-init-config` | выгрузка всех настроек по умолчанию в папку с конфигами |

Посмотреть итоговый конфиг без запуска: `uv run cy-train --cfg job`. Чтобы держать его
файлом рядом с данными, а не читать через флаг, — см. [Своя папка с конфигами](#своя-папка-с-конфигами).

## Быстрый старт

```bash
# разметка из датасета YOLO
uv run cy-ground-truth data_yaml=data.yaml output=ground_truth.csv

# весь конвейер
uv run cy \
    clearml.project_name=detection \
    clearml.task_name=yolo11n-v3 \
    ground_truth=ground_truth.csv \
    train.ultralytics.data=data.yaml \
    train.ultralytics.epochs=300

# только метрики по готовым предсказаниям
uv run cy-metrics predictions=runs/predictions.csv ground_truth=ground_truth.csv
```

Первый шаг здесь обязателен, а не для примера: без готового CSV разметки `cy` откажется
запускаться. Это и остальное, что ломается в первый раз, — в разделе
[Первый запуск](#первый-запуск).

Обратите внимание: у отдельных приложений ключи задаются без префикса
(`cy-train ultralytics.epochs=1`), а в конвейере — с префиксом этапа
(`cy train.ultralytics.epochs=1`).

## Первый запуск

Здесь собрано то, обо что спотыкаются в первый раз. Порядок — тот, в котором это
встречается.

### 1. `uv sync` тянет зависимости из git и всю CUDA-сборку torch

`digital-metrics` и `report-generator` ставятся прямо из GitHub, поэтому нужен доступ к
обоим репозиториям, а не только к PyPI. Python закреплён на 3.12 (`>=3.12,<3.13`) — на
3.13 разрешение зависимостей не сойдётся. Первая синхронизация выкачивает torch с
CUDA-стеком, так что она долгая и объёмная даже на машине без карты.

### 2. `cy` по умолчанию ходит в ClearML — и падает, если он не настроен

`clearml.enabled` включён, а задача ClearML создаётся **первым делом**, до всякого
обучения. Без `~/clearml.conf` и без переменных `CLEARML_*` SDK берёт свой публичный хост
по умолчанию и падает с ошибкой авторизации 401 — на сервере, о котором вы не просили.

```bash
uv run clearml-init                  # настроить свой сервер
uv run cy clearml.enabled=false ...  # прогнать без сервера вообще
```

Ошибка 401 приходит и от **устаревшего** `~/clearml.conf`: `debug.ping` у ClearML
отвечает вообще без ключей, поэтому сервер выглядит живым ровно до первого запуска.
`./scripts/check_env.sh` проверяет настоящим `auth.login`, поэтому ловит это до запуска, а
не посреди него.

### 3. Разметка нужна до запуска `cy`

`ground_truth` по умолчанию — `ground_truth.csv` в текущем каталоге, и его читают этапы
предсказаний, метрик и сравнения. Конвейер проверяет файл **до обучения** и, если его нет,
сразу говорит, чем он делается:

```
FileNotFoundError: ground_truth=... does not exist, and the predict, metrics stage(s)
read it. Write it first with `cy-ground-truth data_yaml=<your data.yaml> output=...`.
```

Поэтому `cy-ground-truth` — не «первая команда в примере», а обязательный шаг перед `cy`:

```bash
uv run cy-ground-truth data_yaml=data.yaml output=ground_truth.csv
```

В CSV записываются **абсолютные** пути изображений, так что перенести его на другую машину
или в другой каталог нельзя — там его нужно построить заново.

### 4. Без своих значений вы обучаетесь на демо-датасете

В `train.yaml` записаны `data: coco8.yaml`, `model: yolo11n.pt` и `epochs: 100`.
`coco8.yaml` — это восьмикартиночный пример из самого ultralytics: он найдёт его внутри
своего пакета и скачает изображения в свой каталог датасетов (`DATASETS_DIR`, по умолчанию
`~/datasets`), а веса — с GitHub. В логе это никак не отличается от обучения на ваших
данных. Всегда задавайте `train.ultralytics.data` явно.

### 5. `clearml.enabled=false` требует `skip_compare=true`

Сравнение ищет прод-модель в ClearML, а при выключенном трекинге искать негде. Это тоже
проверяется до обучения:

```
ValueError: The comparison stage resolves its baseline out of ClearML, but
clearml.enabled=false leaves it no project to search. Pass skip_compare=true to run
without the comparison, or name the baseline task outright with report.baseline.task_id=<id>.
```

Прогон без сервера всегда выглядит так:

```bash
uv run cy clearml.enabled=false skip_compare=true ...
```

### 6. Первый запуск в пустом проекте не даёт ни отчёта, ни сравнения — и завершается успешно

Прод-моделью берётся последняя завершённая задача **с тегом `prod`**. В новом проекте
такой нет, поэтому отчёт получается пустым, сравнение пропускается, а `cy` завершается
кодом 0. Отличие от нормального запуска — две строки WARNING в логе. Чтобы следующему
запуску было с чем сравниваться, этот нужно пометить:

```bash
uv run cy ... clearml.tags=[prod]
```

### 7. `--config-dir` без `--config-name` молча игнорирует вашу папку

Имя конфига у каждого приложения своё и задаётся вторым флагом; `--config-dir` лишь
добавляет каталог в пути поиска. С одним флагом запуск идёт на встроенных настройках, а
ваши правки не читаются — без ошибки и без предупреждения. Подробнее — в
[Своя папка с конфигами](#своя-папка-с-конфигами), там же про то, какие оверрайды после
выгрузки меняют форму.

### И ещё два места

- **Занятая карта выглядит как зависание.** По умолчанию карту дисквалифицирует один
  чужой CUDA-процесс, а ждать запуск готов час. См. [Ожидание свободных карт](#ожидание-свободных-карт).
- **`skip_train=true` без `weights`** берёт чекпоинт по шаблону `runs/detect/<имя>/weights/best.pt`.
  Ultralytics же разводит одноимённые запуски по папкам `<имя>2`, `<имя>3`, поэтому шаблон
  указывает на **самый первый** из них. Если запусков с таким именем было несколько,
  задавайте `weights=` явно.

## Общие ключи конвейера

Значения, которые нужны нескольким этапам, задаются один раз на верхнем уровне, а
конвейер сам передаёт их каждому этапу; в блоке этапа остаётся только то, что решает
этот этап один. Дублировать их под разными именами не нужно — и, что важнее, нельзя
изменить одному этапу и молча забыть про другой:

| Ключ | Куда попадает |
|---|---|
| `clearml.project_name`, `clearml.task_name` | все этапы; `task_name` заодно становится именем папки запуска, если `train.ultralytics.name` не задан |
| `ground_truth` | `predict`, `metrics`, `compare` |
| `splits` | `predict`, `metrics`, `report` |
| `auto_gpu.*` | `train`, `predict`, `compare` |
| `weights`, `skip_train` | `predict`, `compare`; не задан — чекпоинт, который допишет `train`; задан вместе с `skip_train=true` — обучение внутри конвейера пропускается, и оба этапа берут его как есть |

Так же связаны и цепочки «продюсер → потребитель», только теперь их несёт конвейер, а
не ссылка на чужой ключ: чекпоинт, который допишет `train` (или `weights`, если обучение
пропущено), уходит в `predict.weights`, `predict.output` — в `metrics.predictions`,
`metrics.output_dir` — в `report.metrics_dir`, `train.ultralytics.model` — в
`predict.model` (батч подбирается по той архитектуре, которой обучена модель), настройки
инференса сравнения (`conf`, `iou`, `imgsz`, `batch`, `quantize`, `model`, `image_name`) —
из уже посчитанного `predict`, а
`metrics.evaluation.iou_threshold`/`matching_strategy` — в
`compare.iou_threshold`/`matching_strategy`, чтобы сравнение считалось на том же IoU, на
котором калибровались пороги. Внутри конвейера ни один из этих ключей не задать в блоке
своего этапа — их подставляет сам запуск, а не файл конфига.

Разрешение инференса конвейер не передаёт: `predict.ultralytics.imgsz` не задан, и его
читает сам чекпоинт. Ultralytics записывает всю конфигурацию обучения в каждый `.pt`, и
это единственный источник, который не может разойтись с весами, которые описывает — в
том числе для запуска, который обучение пропустил и получил чужую модель. Так же ведут
себя `cy-predict` и `cy-compare` вне конвейера.

Заданное явно число побеждает, но никогда не молча. Вне конвейера — в `cy-predict`,
`cy-compare` и в запуске с `skip_train` — расхождение с чекпоинтом остаётся
предупреждением: считать модель на другом масштабе бывает нужно. Но оба разрешения, и то,
на котором обучались, и то, на котором считали, уходят в запись запуска: таблицей
`predict/resolution` на вкладке plots в ClearML и листом `inference_resolution` в рабочей
книге `report_dev_<сплит>.xlsx` — в том числе в той копии, которую хранит ClearML.

Внутри же конвейера, который сам обучает модель, расхождение между
`train.ultralytics.imgsz` и явно заданным `predict.ultralytics.imgsz` — это отказ, и до
обучения, а не после него. Измерять только что обученную модель на масштабе, которого она
не видела, никто не хочет, а чекпоинт, с которым сверяется предупреждение, до конца
обучения не существует — то есть цена вопроса иначе равна всему обучению. Выход из отказа
запуск называет сам: оставить `predict.ultralytics.imgsz` пустым либо обучать на том же
разрешении.

Прод-модель в конвейере тоже называется один раз — ключами `report.baseline.*`
(`task_id`, `project_name`, `task_name`, `tags`): именно эту задачу конвейер передаёт
сравнению, а не два независимых поиска по проекту, которые могли бы найти разные запуски
— отчёт против одной модели рядом со сравнением против другой. Группы
`compare/baseline_model` внутри конвейера нет: локальный чекпоинт прод-модели на диске —
задача отдельного `cy-compare`.

Единственное, чего сама схема конфига гарантировать не может, — что этап, выбирающий
*один* сплит из общего списка (`metrics.calibration_split`, `compare.split`), выберет
тот, который в этом списке есть. Это по-прежнему проверяется до обучения, а не после
него.

Конвейер создаёт один эксперимент, к которому подключаются все стадии. При
самостоятельном запуске этап добавляет свой суффикс (`yolo11n-v3/metrics`), и ключи там
задаются без префикса: `cy-metrics ground_truth=...`.

Кандидата сравнения в конвейере задать нельзя: он всегда собирается из чекпоинта, который
этот запуск обучил, и порогов, которые откалибровал этап метрик. Группа
`candidate_model` есть только у отдельного `cy-compare`.

Обучение внутри конвейера можно пропустить и прогнать остальные этапы по готовой модели:

```bash
uv run cy skip_train=true weights=runs/detect/prev/weights/best.pt
```

Отключить трекинг целиком: `clearml.enabled=false`. Вместе с ним нужен и
`skip_compare=true` — почему, см. [Первый запуск](#первый-запуск).

## Параметры ultralytics

Все параметры ultralytics видны в конфиге — не через словарь-«прочее», а отдельным
файлом на этап:

```
conf/ultralytics/train.yaml     # всё, что читает обучение детекции
conf/ultralytics/predict.yaml   # всё, что читает предсказание
```

Файлы собраны из `cfg/default.yaml` самого ultralytics вместе с его комментариями, так
что каждый ключ объясняет себя сам. Ключи, которые этот этап не читает — экспорт,
сегментация, поза, obb, глубина, трекер, отрисовка, — не выброшены, а перенесены под
заголовок `# ---- ignored by detection ... ----` и закомментированы. Тест сверяет
объединение живых и закомментированных ключей с установленным `default.yaml`, поэтому
обновление ultralytics, добавившее параметр, роняет прогон тестов, а не прячет ключ.

`null` в файле означает «решает запуск»:

| Ключ | Чем заполняется |
|---|---|
| `batch`, `device` | `auto_gpu` — см. «Авто-выбор GPU» |
| `compile` (оба этапа), `amp` (только обучение) | на GPU — **включены**; на CPU выключены |
| `quantize` (только предсказание) | на GPU — `16` (FP16); на CPU — `32` (FP32): обычная точность, а не «выключено» |
| `name` (обучение) | имя эксперимента ClearML, так что папка запуска всегда совпадает с ним |
| `imgsz` (предсказание) | разрешение, записанное в чекпоинте |

Обратите внимание: `compile` по умолчанию **включён**, хотя у самого ultralytics
`compile: False`. Так же и `quantize`: у ultralytics по умолчанию FP32, здесь на карте —
FP16. Обе настройки меняют сами рамки, поэтому пороги, откалиброванные с ними, не
переносятся на запуск без них — нужна перекалибровка, а не смешивание. Чтобы повторить
старые числа, впишите `compile: false` / `quantize: 32`.

Записанное значение уходит в ultralytics как есть, и код его не перекрывает. Правило
одно на всё: `train_kwargs`/`predict_kwargs` и отдельная развилка `half`/`quantize`
больше не нужны.

`quantize` конвейер передаёт из `predict` в сравнение, а `compile` — нет: сравнение
компилирует по своей карте. Внутри одного сравнения обе модели всегда в одном режиме
(карта у них общая), так что само сравнение честно; расходится только воспроизведение
между запусками, если `compile: false` закреплён в `predict.yaml`.

Набор выбирается целиком по имени файла, а один ключ — точкой:

```bash
uv run cy-train --config-dir ./conf ultralytics=highlr   # conf/ultralytics/highlr.yaml
uv run cy-train ultralytics.lr0=0.02
uv run cy --config-dir ./conf ultralytics@train.ultralytics=highlr
uv run cy train.ultralytics.epochs=5 predict.ultralytics.conf=0.005
```

Свой файл виден только через `--config-dir`: без него приложение ищет набор в
установленном пакете и на `ultralytics=highlr` отвечает `Available options in
'ultralytics': predict, train`. Отдельный ключ точкой (`ultralytics.lr0=0.02`) работает и
без флага.

Файл — конфиг этого проекта, а не готовый вход для `yolo train cfg=...`: ultralytics
отвергает `batch: null` и `compile: null`. Чтобы повторить запуск голым ultralytics,
берите `runs/detect/<name>/args.yaml` — его пишет сам ultralytics со всеми
подставленными значениями.

## Инференс

`predict.ultralytics.batch` — это и размер батча, и главный рычаг по памяти: столько изображений
одновременно декодируется и уходит в сеть. Уменьшайте его (или `imgsz`), чтобы влезть в
карту поменьше. Не задан — размер подберёт `auto_gpu` (см. «Авто-выбор GPU»).

Важно: батч меняет не только память, но и сами рамки. Ultralytics леттербоксит с
`auto=same_shapes and rect`, где `same_shapes` считается по изображениям *одного батча*, а
`rect` для предсказания по умолчанию включён. Батч, в котором у всех изображений
одинаковый размер, дополняется до наименьшего подходящего прямоугольника, а батч из
разных — до полного квадрата: другой вход, другие детекции у одного и того же
изображения. Поэтому батч входит в ключ кэша предсказаний сравнения, а пороги переносятся
через смену батча не лучше, чем через смену `imgsz`. Прямоугольный леттербокс
выключается: `predict.ultralytics.rect=false`.

Список изображений уходит в ultralytics файлом-манифестом `.txt`, а не списком в памяти.
Только так `batch` вообще учитывается (список целиком становится одним проходом сети — это
и медленнее, и кратно прожорливее по видеопамяти), только так в `Results.path` приходит
настоящий путь, а не `image0.jpg`, и только так изображения читаются тем же вызовом
OpenCV, что и при обучении, без разворота по EXIF. Ultralytics сортирует манифест, поэтому
рамки привязываются к изображению по пути, а не по позиции; изображение, которое не
удалось прочитать, ultralytics просто пропускает с предупреждением, поэтому перед
возвратом проверяется, что посчитаны все запрошенные.

На CUDA по умолчанию включены половинная точность и `torch.compile` — обе выигрывают тем
сильнее, чем тяжелее модель. На маленькой модели выигрыша нет: сеть занимает меньшую часть
времени, чем препроцессинг, постпроцессинг и декодирование вместе, так что ускорять её
нечем — FP16 на замерах вышел даже чуть медленнее, а `compile` берёт разовую плату за
компиляцию, которую сплит такого размера не успевает отбить. В конвейере эта плата вносится
один раз: этап предсказаний и обе стороны сравнения идут в одном процессе, поэтому вторая
модель проходит тот же сплит заметно быстрее первой.

Половинная точность передаётся как `quantize=16`, а не `half`: в ultralytics 8.4 `half`
объявлен устаревшим и в `default.yaml` его больше нет. Достаточно записать `quantize` в
конфиге, чтобы решение перешло к вам целиком.

Важно: обе настройки меняют сами рамки, то есть меняют и все откалиброванные пороги.
Пороги, посчитанные без них, не переносятся — нужна перекалибровка, а не смешивание.
Выключаются по отдельности:

```bash
uv run cy-predict ultralytics.quantize=32 ultralytics.compile=false
```

## Обучение

Обучение идёт в смешанной точности (`amp=True`) и с `torch.compile` — здесь компиляция
окупается заведомо, потому что оплачивается один раз и размазывается по всем эпохам.
Половинная точность обучения — это именно AMP, а не `quantize`: тот приводит сами веса,
чего обучение делать не может. Обе настройки задаются явно, а не оставляются на умолчание
зависимости, и перекрываются записью в `conf/ultralytics/train.yaml` или с командной
строки:

```bash
uv run cy-train ultralytics.amp=false ultralytics.compile=false
```

## Авто-выбор GPU

По умолчанию `auto_gpu.enabled=true`: NVML опрашивает все карты, отбрасывает занятые
чужими процессами и заполненные, а затем подбирает батч под модель и под самую слабую из
выбранных карт.

### Откуда берётся батч

`batch` не задан (значение по умолчанию) — решает `auto_gpu`. Задан числом — используется
ровно это число, в том числе при включённом `auto_gpu`: выбор свободных карт и выбор
батча независимы. Итоговый `batch` всегда кратен числу устройств (ultralytics делит общий
батч между рангами без проверки кратности).

Так же независим и `device`. Не задан — карты выбирает опрос NVML. Задан
(`device=1`, `device=0,1`, `device=cuda:1`, `device=cpu`) — запуск идёт ровно на этих
картах, а `auto_gpu` подбирает под них только батч. Раньше обучение при включённом
`auto_gpu` писало предупреждение и выбрасывало заданный `device`, тогда как этап
предсказаний его учитывал: одно и то же слово в конфиге означало разное на разных этапах.
Теперь правило одно на все этапы.

Когда решает `auto_gpu`, отвечает первый источник, у которого есть ответ. Какой именно —
всегда видно в логе, чтобы неверное число можно было исправить там, где оно задано:

| Источник | Масштабируется по VRAM |
|---|---|
| `auto_gpu.batch_table` — таблица, измеренная на этом железе | нет |
| батч, на котором этот этап уже доходил до конца (см. ниже) | нет |
| `auto_gpu.model_batch_per_gpu[<модель>]` — опора для этой модели | да |
| `auto_gpu.batch_per_gpu` — одна опора на всё | да |

Первые два — измерения, поэтому используются как есть, без пересчёта по видеопамяти и без
округления вниз до степени двойки. Последние два — батч на эталонной карте, поэтому оба
проходят через отношение `видеопамять карты / reference_vram_gb`.

```bash
uv run cy-train auto_gpu.batch_per_gpu=16 auto_gpu.reference_vram_gb=24
uv run cy-train '+auto_gpu.model_batch_per_gpu={yolo11n:32,yolo11x:8}'
```

`model_batch_per_gpu` по умолчанию пуст, поэтому из командной строки он, как и
`batch_table`, задаётся с `+`: без плюса Hydra отвечает `Key 'yolo11n' is not in struct`.

`batch_per_gpu` — ваш оптимальный батч на одну карту при `reference_vram_gb` видеопамяти.
`model_batch_per_gpu` — то же самое, но отдельно для каждой модели: yolo11n и yolo11x
влезают в карту по-разному, и одна опора не может быть верной для обеих. Ключ — имя весов
без расширения (`yolo11x.pt` → `yolo11x`).

Важно: `reference_vram_gb` — не потолок памяти, а знаменатель. Батч считается как
`batch_per_gpu × видеопамять карты / reference_vram_gb`, поэтому поднять его «под свою
карту побольше» значит **уменьшить** батч, а не разрешить больший. Меняют здесь
`batch_per_gpu` — то, сколько влезает; `reference_vram_gb` описывает лишь ту карту, на
которой это измерили.

### Таблица батчей

`auto_gpu.batch_table` — числа, которые вы измерили на этом железе: модель → карта → число
карт. Уровень «число карт» можно опустить, написав батч прямо у карты, — тогда он годится
при любом их количестве. Настраивается один раз и больше на этой машине не меняется.

```yaml
auto_gpu:
  batch_table:
    yolo11m:
      rtx 5090: 32
    yolo11x:
      rtx 5090:
        1: 12
        2: 8
```

Ключ карты ищется как подстрока того имени, которое возвращает драйвер, поэтому и
`5090`, и `rtx 5090` находят `NVIDIA GeForce RTX 5090`; при нескольких совпадениях
побеждает самое длинное. Регистр и лишние пробелы не важны. Если для модели и карты запись
есть, а для нужного числа карт — нет, приложение пишет об этом и идёт к следующему
источнику, а не угадывает.

Обратная сторона подстроки: слишком общий ключ находит не ту карту. `3090` совпадёт и с
`RTX 3090`, и с `RTX 3090 Ti`, а на машине с разными картами это уже другой батч. Пишите
ключ настолько длинным, чтобы он различал карты, которые у вас есть.

Из командной строки то же самое задаётся так (кавычек вокруг ключа с пробелом грамматика
Hydra не принимает — пробел экранируется, либо берётся ключ покороче, без пробела):

```bash
uv run cy-train '+auto_gpu.batch_table={yolo11x:{rtx\ 5090:6}}'
uv run cy-train +auto_gpu.batch_table.yolo11x.5090=6
```

### Запомненный батч

Батч, на котором этап дошёл до конца, записывается в файл и в следующий раз берётся
оттуда. Так число, найденное однажды вручную, больше не приходится вводить:

```bash
uv run cy-train ultralytics.batch=48   # прошло — значит запомнено
uv run cy-train                        # батч 48 и без указания
```

Путь — `$CLEARML_YOLO_BATCH_TABLE`, по умолчанию `~/.cache/clearml-yolo/batch_table.json`.
Записывается только успех, и только больший батч: то, что влез маленький, не говорит
ничего, а то, что дошёл до конца большой, доказывает и все меньшие. Этапы хранятся
отдельно — обучение и инференс держат разную память, поэтому результат одного ничего не
говорит про другой. `cy-compare` читает записи `predict`, но своих не оставляет: его успех
относится сразу к двум моделям, а это неоднозначное свидетельство.

Ничего не записывается, если карты не опрашивались: при `auto_gpu.enabled=false`, при явном
`device` **вместе с** явным `batch`, на CPU, при батче `-1` и когда имя модели неизвестно.
Один только явный `device` опрос не отменяет — карты за ним всё равно осматриваются, чтобы
подобрать батч, и результат запоминается как обычно. Хранение целиком отключается:

```bash
uv run cy-train auto_gpu.remember_batch=false
```

Таблица из конфига всегда старше запомненного: файл — это кэш, а число, которое вы
написали руками, — решение.

Помните, что этот кэш — невидимое состояние: он читается **раньше**, чем опора по
видеопамяти, и переживает смену `imgsz` и версии окружения. Запуск, который «вдруг» пошёл
на непонятном батче, скорее всего взял его отсюда — в лог при этом уходит строка о том,
какой запуск и когда его оставил. Сбросить — удалить файл или запускать с
`auto_gpu.remember_batch=false`.

### Ожидание свободных карт

Запуск не падает, если все карты заняты, — он ждёт. Каждые `wait_poll_seconds` в лог
уходит строка с тем, сколько карт нужно и сколько доступно; по истечении
`wait_timeout_seconds` запуск завершается ошибкой. На CPU он при этом не переключается:
незаметное стократное замедление выглядит ровно как успешный запуск.

```bash
uv run cy-train auto_gpu.wait_poll_seconds=60 auto_gpu.wait_timeout_seconds=7200
uv run cy-train auto_gpu.wait_for_free=false   # падать сразу, как раньше
```

Учтите умолчания: `max_compute_processes: 0` дисквалифицирует карту от **одного** чужого
CUDA-процесса, а `wait_timeout_seconds` — час. На рабочей станции, где открыт браузер,
ядро Jupyter или недобитый прошлый запуск, это выглядит как зависший `cy`: строка ожидания
раз в полминуты и никакой ошибки до конца часа. Если ждать не нужно —
`auto_gpu.wait_for_free=false` скажет об этом сразу.

`max_compute_processes` — сколько чужих процессов на карте допустимо (по умолчанию 0).
Процессы самого запуска чужими не считаются: инференс после обучения идёт в том же
процессе, и иначе он ждал бы карту, которой уже владеет.

Под WSL NVML не возвращает список процессов вообще, как бы занята карта ни была, поэтому
занятость там определяется через ядро: каждый GPU-клиент WSL держит открытым `/dev/dxg`,
и приложение считает соседей по нему. `max_compute_processes` работает как обычно.
Подмена включается, только если NVML не назвал вообще никого: где NVML работает, он
точнее — `/dev/dxg` один на все карты и не даёт понять, какая именно занята.

Отсюда следствие для WSL с несколькими картами: `/dev/dxg` общий, поэтому один чужой
GPU-процесс помечает занятыми **все** карты сразу, и запуск уходит в часовое ожидание.
Приложение об этом предупреждает в логе. Лечится либо освобождением карты, либо явным
`ultralytics.device=[0]`.

Остаётся один случай, который изнутри Linux не виден: память, занятую хостом Windows
или другим пользователем, не держит ни один здешний процесс. Приложение пишет об этом в
лог, а защитой служат пороги по памяти — их стоит ужесточить:

```bash
uv run cy-train auto_gpu.min_free_vram_gb=24 auto_gpu.max_used_fraction=0.1
```

### Резерв под инференс

`auto_gpu.reserve_gpus` (по умолчанию 1) оставляет карты другим запускам, чтобы их
инференс дошёл до конца. Резерв ограничивается так, чтобы запуску всегда досталась хотя
бы одна карта: на машине с одной картой буквальная политика не дала бы обучаться
никогда. Сам инференс резерв игнорирует — резерв существует ради него.

```bash
uv run cy-train auto_gpu.reserve_gpus=2   # оставить две карты соседям
uv run cy-train auto_gpu.reserve_gpus=0   # занять всё
```

Ручной режим (`device` и `batch` — параметры ultralytics, поэтому идут с их префиксом;
`device=...` без него не пройдёт компоновку — `Key 'device' not in 'Config'`):

```bash
uv run cy-train auto_gpu.enabled=false ultralytics.device=[0,1] ultralytics.batch=32
uv run cy auto_gpu.enabled=false train.ultralytics.device=[0,1] train.ultralytics.batch=32
```

`batch=-1` (автоподбор ultralytics) работает только на одной карте — на нескольких
приложение сообщит об ошибке сразу, а не в середине обучения. То же самое и когда карты
выбирает `auto_gpu`: в сообщении будет сказано, что число карт ограничивается через
`auto_gpu.max_gpus`.

`cy-compare` резолвит батч по модели-кандидату. Если прод-модель тяжелее, батч, который
подойдёт обеим, нужно задать руками — и рычаг разный в двух режимах:

```bash
uv run cy-compare inference.batch=8            # отдельный запуск
uv run cy predict.ultralytics.batch=8          # внутри конвейера
```

Внутри `cy` у сравнения своего батча нет вовсе: `conf`, `iou`, `imgsz`, `batch` и
`quantize` конвейер копирует из `predict` поверх всего, что там записано, — чтобы
сравнение прогоняло обе модели ровно тем же инференсом, каким считался кандидат.

## Данные

Для обучения нужен обычный `data.yaml`. Для метрик — CSV разметки со столбцами
`image_name, instance_label, bbox_x_tl, bbox_y_tl, bbox_x_br, bbox_y_br, split`
(абсолютные пиксели, углы рамки; классы именами, не индексами). Для `cy-predict`
дополнительно нужен `image_path`.

Изображение должно принадлежать ровно одному сплиту: digital-metrics отклоняет
пересечения, потому что калибровка порогов утекала бы в оценку.

### На чём спотыкается настоящий датасет

- **Имена файлов должны быть уникальны на весь датасет.** digital-metrics опознаёт
  изображение по `image_name`, а не по пути, поэтому `train/img_001.jpg` и
  `val/img_001.jpg` в одном датасете — это ошибка, и `cy-ground-truth` откажется работать,
  а не выберет одно из двух. Разложите или переименуйте до разметки.
- **Только рамки.** Метки сегментации и позы отвергаются с указанием файла и числа полей:
  ожидается ровно `class cx cy w h`.
- **Датасет без `test`.** Если в `data.yaml` есть только `train` и `val`, половина `val`
  переносится в сплит `test` (`ground_truth.test_fraction`, по умолчанию 0.5). Сообщение об
  этом уходит в лог одной строкой INFO — и легко проходит мимо глаз. Значит, «тестовые»
  метрики посчитаны на части валидации; если это не то, чего вы хотели, задайте `test` в
  самом `data.yaml`.
- **Относительный `path:` внутри `data.yaml`.** Его разрешает ultralytics, и если путь не
  находится относительно текущего каталога, он ищется в каталоге датасетов ultralytics
  (`DATASETS_DIR`, по умолчанию `~/datasets`), а не рядом с самим yaml. Самый частый
  источник «изображения же вот тут». Абсолютный `path:` снимает вопрос.
- **Сам `data.yaml`** ищется относительно текущего каталога, а потом внутри установленного
  пакета ultralytics. Опечатка в имени даёт короткое `FileNotFoundError: '<имя>' does not
  exist` — без указания на то, где именно его искали, так что проверять путь придётся
  самостоятельно.

## Метрики и артефакты

Метрики считаются отдельно для каждого сплита (`splits=[train,val,test]`), пороги
калибруются на `calibration_split=val`. Для самого `val` пороги подбираются по нему же,
так как калибровать сплит по себе нельзя.

Имя каждого артефакта начинается с этапа, который его создал. Вкладка ARTIFACTS в
ClearML своей группировки не имеет (там четыре фиксированных раздела, пользовательские
артефакты попадают в OTHER и сортируются по алфавиту), так что префикс — единственное,
что собирает артефакты одного запуска рядом:

| Этап | Артефакты |
|---|---|
| `predict` | `predict_predictions` |
| `metrics` | на каждый сплит: `metrics_dashboard_full_*`, `metrics_dashboard_dtrk_*`, `metrics_matches_gt_*`, `metrics_matches_preds_*`, `metrics_summary_*`, `metrics_raw_*`, `metrics_best_confidences_*` |
| `report` | `report_dev_*`, `report_business_*` |
| `compare` | `compare_workbook_*` |

Настоящие сворачиваемые разделы есть на вкладках PLOTS и SCALARS. В PLOTS появляются
разделы `metrics` (таблица метрик по классам, по одной серии на сплит), `report`
(метрики прод-модели, с которой шло сравнение — на диске они лежат во временном файле и
раньше в UI не попадали) и `comparison` / `comparison_degraded` /
`comparison_methodology`. В SCALARS — по одной карточке на сплит (`metrics_test`,
`metrics_val`, …) со средними значениями.

Имена изменились в этом релизе без обратной совместимости: `report.baseline` и
`cy-compare` читают артефакты **прошлых** задач, поэтому задача, созданная до
обновления, своих дашбордов уже не найдёт. Причём не упадёт: поиск прод-задачи проходит
успешно, а дальше на каждый сплит пишется «нет артефакта для сплита», отчёт получается
пустым и запуск завершается кодом 0. Папку с конфигами, выгруженную до этого релиза, нужно
перегенерировать — в ней остался `artifact_prefix: dashboard_full`.

## Сравнение с предыдущей моделью

```bash
# базовая модель из прошлой задачи ClearML (по умолчанию — последняя завершённая)
uv run cy-report baseline=clearml baseline.project_name=detection

# из локальной папки
uv run cy-report baseline=local baseline.directory=runs/previous/metrics

# без сравнения
uv run cy-report baseline=none
```

Внутри конвейера группа называется `report/baseline`:
`uv run cy report/baseline=local report.baseline.directory=...`. В своей папке с конфигами
эта группа выбирается иначе — см. [Своя папка с конфигами](#своя-папка-с-конфигами).

На каждый сплит создаётся два файла: `report_dev_{split}.xlsx` (4 листа) и
`report_business_{split}.xlsx` (5 листов, включая вердикт «К выкатке» / «Не к выкатке»).
Сравнение считается как новая модель минус прод.

Классы с числом train-примеров ≤ `min_train_count` (по умолчанию 20) исключаются из
сравнения и попадают на лист «Удаленные классы». Порог меняется своим конфигом:

```bash
uv run cy-report report_config_path=my_report_config.yaml
```

## Сравнение двух обученных моделей

`cy-report` сравнивает дашборды: числа старой модели посчитаны на тех изображениях,
которые видел тот запуск. `cy-compare` вместо этого прогоняет оба чекпоинта по
**текущей** разметке — одни и те же изображения, один и тот же код инференса, — и
считает, значима ли разница. Обучение для этого не нужно: обе модели берутся из ClearML
по id задачи.

```bash
uv run cy-compare \
    baseline_model.task_id=<id прод-модели> \
    candidate_model.task_id=<id новой модели> \
    ground_truth=ground_truth.csv split=test output_dir=runs/comparison
```

В конвейере `cy` сравнение — последний этап и включено по умолчанию. Новой моделью
берётся та, которую этот запуск только что обучил, с порогами, откалиброванными его же
этапом метрик; из конфига она не берётся, иначе можно было бы сравнить не то, что
построили.

Прод-моделью по умолчанию берётся **последняя завершённая задача с тегом `prod`**, а не
просто последняя завершённая: последним закончиться с тем же успехом мог неудачный
эксперимент. Модель повышается тегом при запуске или уже после него:

```bash
uv run cy ... clearml.tags=[prod]                 # пометить сразу
uv run cy ... report.baseline.task_id=<id>        # явная прод-модель
uv run cy ... 'report.baseline.tags=[]'           # любая последняя, в обоих отчётах
uv run cy ... skip_compare=true                   # без сравнения
```

Прод-модель называется один раз — ключами `report.baseline.*`, — и именно эту задачу
конвейер передаёт сравнению, так что «прод модель» в отчёте и в сравнении —
гарантированно одна и та же задача, а не два одинаково настроенных поиска. Группы
`compare/baseline_model` внутри конвейера нет: переопределить прод-модель для сравнения
отдельно от отчёта нельзя, и локальный чекпоинт вместо задачи ClearML внутри `cy` тоже
недоступен — это по-прежнему задача отдельного `cy-compare`, у которого группа своя —
`baseline_model.task_id=<id>`.

Если сравнивать не с чем — первый запуск в пустом проекте или пропущенный этап метрик, —
этап пишет предупреждение и пропускается: отчётность не должна ронять запуск, который уже
дал валидные результаты.

Здесь важно различие: «искали и не нашли» — предупреждение, а «искать негде» — ошибка, и
она поднимается **до** обучения. Второе — это `clearml.enabled=false` без
`skip_compare=true`: прод-модель конвейер берёт только из ClearML, поэтому с выключенным
трекингом сравнение не могло бы состояться ни при каком исходе.

Локальные чекпоинты тоже подходят, но тогда пороги задаются вручную: они калибруются
этапом метрик, и брать их из дашборда нельзя — там они округлены.

```bash
uv run cy-compare baseline_model=local candidate_model=local \
    baseline_model.weights=prod.pt candidate_model.weights=new.pt \
    'baseline_model.thresholds={car:0.31,truck:0.44}' \
    'candidate_model.thresholds={car:0.35,truck:0.40}'
```

На выходе — `compare_workbook_{split}.xlsx` с тремя листами (сравнение по классам, исключённые
классы, методика) и таблицы в ClearML. Precision проверяется бутстрэпом по изображениям,
recall — точным тестом Макнемара; все гипотезы сплита (две на класс) корректируются
Benjamini-Hochberg разом. Строка «Итого» в семью не входит: это сводка тех же данных, и
включить её значило бы посчитать одно свидетельство дважды.

Класс, которого нет в словаре одной из моделей, исключается, а не получает нулевой
recall: модель, не знающая класса, не «плохо его находит».

## Своя папка с конфигами

`cy-init-config` выгружает все настройки по умолчанию — по одному файлу на команду плюс
папку `ultralytics/` с параметрами ultralytics (см. «Параметры ultralytics»):

```bash
uv run cy-init-config ./conf
uv run cy --config-dir ./conf --config-name cy
uv run cy-train --config-dir ./conf --config-name cy-train
```

**Оба флага обязательны.** `--config-dir` только добавляет каталог в пути поиска, а имя
конфига у каждого приложения своё и зашито в код. `uv run cy --config-dir ./conf` без
`--config-name cy` запускается как ни в чём не бывало — и берёт конфиг из установленного
пакета, а вашу папку не открывает вовсе. Ни ошибки, ни предупреждения: правки просто не
применяются. Проверить, что читается именно ваш файл, можно так же, как и всё остальное, —
`--cfg job`.

Файлы названы по команде, а не по конфигу: Hydra больше не подставляет структурный
конфиг под одноимённый YAML, и файл `pipeline.yaml` рядом с записью `pipeline` в сторе —
это ошибка, а не слияние.

`${...}` в этих файлах не встречается: `cy.yaml` не ссылается сам на себя. Ключи, общие
для нескольких этапов (`clearml`, `auto_gpu`, `ground_truth`, `splits`, `weights` — см.
«Общие ключи конвейера»), заданы один раз на верхнем уровне файла, а по этапам их
раздаёт сам конвейер при запуске — не Hydra и не YAML. В блоке своего этапа их поэтому
нет: что ни впиши туда руками (`predict.weights`, `compare.iou_threshold` и так далее),
запуск пересчитает заново и перезапишет, а как оверрайд командной строки такой ключ
вообще не пройдёт компоновку — `predict.weights=...` падает с `Key 'weights' not in
'Config'`. Единственное место для такого значения — самый верхний уровень: `weights=...`.

Папку, выгруженную до того, как параметры ultralytics стали отдельными файлами, нужно
выгрузить заново: в ней остались `train_kwargs`/`predict_kwargs` и десяток ключей
ultralytics в блоках этапов, а папки `ultralytics/` нет вовсе — запуск возьмёт параметры
из установленного пакета и ваших правок не увидит.

Папку, выгруженную до появления авто-подбора батча, нужно выгрузить заново: в ней
`batch: 16` записан числом, а теперь число означает «использовать ровно это» и отключает
подбор.

Папку, выгруженную до того, как конвейер стал раздавать общие ключи сам, тоже нужно
выгрузить заново: в ней остались `predict.weights`, `compare.iou_threshold` и прочие ключи
этапов, которые запуск теперь пересчитывает и молча перезаписывает — правку вы внесёте, а
запуск её не увидит. `predict.imgsz` из той же папки ведёт себя иначе: его конвейер не
заполняет, поэтому старый файл не перезапишется, а не соберётся вовсе. Разрешение решает
чекпоинт (см. «Общие ключи конвейера»).

### Выбор группы в своей папке работает не для всех групп

В списке `defaults` выгрузка сохраняет только наборы ultralytics — они и выбираются по
имени как обычно, хоть со встроенным конфигом, хоть со своей папкой. Остальные группы
записываются готовыми значениями и из списка исчезают, поэтому выбрать их по имени больше
нельзя — только задать значением:

| Со встроенным конфигом | Со своей папкой |
|---|---|
| `cy report/baseline=none` | `cy ... report.baseline.source=none` |
| `cy-report baseline=local` | `cy-report ... baseline.source=local` |
| `cy-compare baseline_model=local` | `cy-compare ... baseline_model.source=local` |

Иначе Hydra отвечает `Could not override 'report/baseline'. No match in the defaults
list.` и предлагает `+report/baseline=none` — этот совет здесь не поможет: ключ нужно
менять значением, а не добавлять группу заново.

Отдельно: шапка, которую `cy-init-config` пишет в начало каждого файла, одна на все
команды и советует `<команда> ultralytics=<имя файла>`. Для отдельных приложений это
верно, а для `cy` — нет: у конвейера две группы наборов, и выбирать нужно
`ultralytics@train.ultralytics=` или `ultralytics@predict.ultralytics=`. Ошибку Hydra в
этом случае подсказывает сама.

## Разработка

```bash
uv run pytest
uv run ruff check .
uv run mypy .
uv run lint-imports
```

`uv run pre-commit install` ставит хук, который выполняет эти четыре команды через
`uv run`, из той же заблокированной группы `dev`, так что версия линтера в хуке и в
терминале не расходятся. Перед ними хук прогоняет ещё несколько общих проверок
(`check-yaml`, `check-toml`, конфликты слияния, размер файлов, пробелы и перевод строки в
конце) — они приходят из отдельного закреплённого репозитория и живут в собственном
окружении pre-commit, а не в группе `dev`.

`lint-imports` проверяет контракты импорта из `pyproject.toml`. Пакет уложен слоями —
`apps` → `config_tree` → `configs` → `tasks` → `comparison` → предметные модули, — и
слой ниже не имеет права знать о слое выше. Отдельные контракты держат SDK по местам:
`clearml` виден только адаптерам `clearml_*` и задачам, hydra не доходит до предметных
модулей, а `ultralytics` и `torch` грузятся лишь там, где действительно нужны веса.
`configs` стоит выше `tasks`, а не ниже: он собирает конфиги из сигнатур самих задач.
