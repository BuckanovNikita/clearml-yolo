# clearml-yolo

`clearml-yolo` — набор приложений Hydra/hydra-zen для обучения YOLO, получения предсказаний,
оценки, отчётов и сравнения моделей. Параметры исполнения передаются
Ultralytics; проект сохраняет воспроизводимые входы, результаты и артефакты в
ClearML.

Подробные требования к поведению приложения собраны в
[указателе документации](docs/current-contracts.md). Документы отдельных выпусков
и датированные результаты проверок описывают состояние проекта на тот момент.

## Установка

`uv add <INTERNAZL_REPO_BOILERPLATE>` или `uv pip install <INTERNAZL_REPO_BOILERPLATE>`.

## Приложения

| Команда | Назначение |
|---|---|
| `cy` | полный конвейер: обучение, предсказания, метрики, сравнение и отчёты |
| `cy-train` | обучение YOLO |
| `cy-predict` | получение предсказаний и сохранение их в таблицу |
| `cy-val` | предсказания по сохранённым весам на `val` и указанных выборках, калибровка и оценка |
| `cy-metrics` | метрики, точные пороги, таблицы, панели показателей и графики |
| `cy-report` | технический и бизнес-отчёты по результатам текущей оценки двух моделей |
| `cy-compare` | сравнение базовой модели и новой модели на одних текущих изображениях выбранной выборки; по умолчанию `test` |
| `cy-ground-truth` | преобразование разметки YOLO из `data.yaml` в CSV |
| `cy-init-config` | создание каталога с примерами конфигураций |

Команда `cy-queue` удалена. Проект не управляет очередью,
арендой GPU, подбором размера пакета и пользовательскими аугментациями из JSON.
Запуск без регистрации результатов в ClearML не поддерживается.
`auto_gpu`, `--force-gpu`, `clearml.enabled=false` и удалённые поля
вызывают явную ошибку.

## Быстрый старт

По умолчанию собственные результаты и хранилища приложения создаются в рабочей директории
запуска. Переменная `CY_HOME` задаёт другой корневой каталог; относительное значение
разрешается при старте команды. Результаты находятся в `runs/`, логи Hydra — в `outputs/`,
кэши подготовленных CSV и копий нативных наборов — в `.cache/clearml-yolo/`, а собственные
временные файлы — в `.tmp/`. Внутри `CY_HOME` также размещаются хранилища Ultralytics,
ClearML и данных/базы FiftyOne. При обучении по нативному YAML изображения и метки
копируются в общий кэш: Ultralytics изменяет копии, сохраняя исходные файлы.

Явно заданные пути и поддерживаемые переменные окружения можно направить в любой каталог.
Если физический путь записи находится внутри домашнего каталога, команда предупреждает,
но сохраняет выбранный путь. Существующие конфигурации ClearML и FiftyOne читаются
без перезаписи. Старые кэши не перемещаются автоматически.

Общие `XDG_CACHE_HOME` и `XDG_CONFIG_HOME`, кэши Python, Torch, CUDA, Triton, Numba,
Hugging Face и Matplotlib, конфигурация ETA/FiftyOne, а также `TMPDIR`, `TMP` и `TEMP`
не перенаправляются через `CY_HOME`. При необходимости изолируйте их в запускающем скрипте.
Подробности — в [контракте каталогов](docs/filesystem-policy.md).

Создайте каталог с редактируемыми примерами:

```bash
uv run cy-init-config ./conf
```

Команда создаёт восемь файлов команд: `cy.yaml`, `cy-train.yaml`, `cy-predict.yaml`,
`cy-val.yaml`, `cy-metrics.yaml`, `cy-report.yaml`, `cy-compare.yaml` и
`cy-ground-truth.yaml`. Они содержат текущие настройки команд и подсказки по
нативным параметрам. Дополнительно создаются группы `ultralytics/default.yaml` и
`ultralytics_predict/default.yaml` с оригинальными комментариями Ultralytics.
Замените обязательные значения `???`, задайте входные пути
и настройки ClearML. Относительные пути считаются от рабочей директории запуска.
Инициализация не требует подключения к ClearML и не создаёт задачу.
Примеры защищены от перезаписи; для замены используйте
`uv run cy-init-config ./conf --force`. Остальные файлы каталога сохраняются.

Запуск с созданной конфигурацией:

```bash
uv run cy-train --config-dir=./conf --config-name=cy-train \
  ground_truth=ground_truth.csv ultralytics.model=yolo11n.pt ultralytics.epochs=10 \
  clearml.project_name=detection clearml.tags='[example]'
```

Для полного конвейера достаточно готового CSV разметки и доступных изображений.
Если исходная разметка в формате YOLO, сначала получите CSV:

```bash
uv run cy-ground-truth data_yaml=data.yaml output=ground_truth.csv
```

Запустите полный конвейер. `run_dir` принадлежит конвейеру и изолирует все его
выходы:

```bash
uv run cy \
  run_dir=./runs/experiment-030 \
  clearml.project_name=detection \
  clearml.task_name=yolo11n-v3 \
  ground_truth=ground_truth.csv \
  ultralytics.epochs=100 \
  ultralytics.device=0 \
  ultralytics_predict.device=0
```

Без явного выходного пути результаты размещаются в
`runs/<безопасное-имя-проекта>/<безопасное-имя-задачи>-<task-id>/`. Имена берутся
из активной задачи ClearML; специальные символы кодируются в один компонент пути.
Структура стадий сохраняется. Явные `run_dir`, `run_id`, `output_dir` и `output`
сохраняют приоритет; `run_id` задаёт `runs/<run_id>/`.

Входные пути обязательны: команды не выбирают файлы из текущей папки по умолчанию.
Для отдельной стадии:

```bash
uv run cy-train ultralytics.data=data.yaml ultralytics.model=yolo11n.pt ultralytics.device=0
uv run cy-predict weights=./weights/best.pt ground_truth=ground_truth.csv \
  output=./runs/predictions.csv ultralytics_predict.device=0
uv run cy-val weights=./weights/best.pt ground_truth=ground_truth.csv \
  output_dir=./runs/validation ultralytics_predict.device=0
```

## Обучение из CSV разметки

`cy` использует `ground_truth` как единственный источник данных для обучения и оценки.
Для отдельного обучения передайте тот же CSV в `cy-train`:

```bash
uv run cy-train ground_truth=ground_truth.csv dataset_format=ndjson \
  ultralytics.model=yolo11n.pt ultralytics.epochs=10 \
  clearml.project_name=detection clearml.tags='[csv-training]'
uv run cy-train ground_truth=ground_truth.csv dataset_format=flat \
  ultralytics.model=yolo11n.pt ultralytics.epochs=10 \
  clearml.project_name=detection clearml.tags='[csv-training-flat]'
```

По умолчанию `dataset_format=ndjson`; альтернативный формат — `flat`. Параметр находится
на уровне команды, а не внутри `ultralytics`. NDJSON сохраняет метаданные и разметку
по изображениям и исходные имена файлов, включая регистр расширений. Оба формата
создают готовый `data.yaml`; обучение читает его напрямую, без повторной конвертации.
Формат `flat` сохраняет нумерованные имена. Совпадающие имена файлов разметки
в одной выборке отклоняются.

CSV содержит столбцы `image_name`, `image_path`, `instance_label`, `bbox_x_tl`,
`bbox_y_tl`, `bbox_x_br`, `bbox_y_br`, `split`. Координаты — углы рамки в пикселях;
`instance_label` — имя класса. `image_name` должен совпадать с именем файла изображения
и однозначно определять его. Относительные `image_path` разрешаются от каталога CSV.
Существующие выборки `train` (обучающая), `val` (валидационная) и `test` (тестовая)
сохраняются без переразбиения; для обучения нужны непустые `train` и `val`,
а для включённой оценки — запрошенные выборки.
Пустые класс и четыре координаты обозначают фоновое изображение.

Некорректные рамки удаляются: неполные, нечисловые, бесконечные, нулевого или отрицательного
размера, выходящие за границы изображения, либо без класса. Перед обучением выводится
сообщение о числе удалённых рамок (`Invalid bounding boxes dropped: N`), включая ноль.
Каждая удалённая рамка учитывается один
раз. Остальные рамки сохраняются; изображение без оставшихся рамок становится фоновым.
Если во всём `train` не осталось корректной рамки, обучение не начинается. Ошибки структуры
CSV, недоступные изображения и противоречивые идентификаторы или выборки
завершают команду с ошибкой.

При CSV-обучении `ultralytics.data` заменяется подготовленными данными, отключаются фильтры
классов и изменение доли набора данных; `single_cls` и переназначение классов также не применяются.
`resume` запрещён: для дообучения укажите файл весов через `ultralytics.model`. Настройки
устройства, размера пакета, автоматической смешанной точности (AMP), эпох и аугментаций
сохраняются. Конвейер использует очищенный CSV для последующих предсказаний,
метрик и сравнения.

`dataset_cache_dir` у `cy` и `cy-train` задаёт общий каталог подготовленных наборов данных.
При `dataset_cache_dir=null` всегда используется
`$CY_HOME/.cache/clearml-yolo/datasets`, независимо от `XDG_CACHE_HOME`. Без настройки
`CY_HOME` это рабочая директория запуска. Явный `dataset_cache_dir` сохраняет приоритет.
Ключ включает SHA-256 байтов CSV, формат и версию подготовки.
Повторный запуск не хеширует и не копирует изображения, не конвертирует NDJSON заново.
Исходные изображения считаются неизменными: одинаковые байты CSV должны ссылаться на те же
изображения. После исправления изображений удалите соответствующую запись кэша, когда она
не используется. Кэш должен находиться вне каталога запуска; очистка запуска его не удаляет.

Запись становится доступна целиком после проверки файлов и выборок. Запуски с одной записью
последовательно удерживают блокировку до завершения обучения: нативное исправление JPEG и
запись вспомогательных кэшей не могут конфликтовать. Разные записи независимы.
Исходный CSV и изображения не меняются. NDJSON, архив меток и диагностика остаются локально;
в ClearML публикуется очищенная таблица разметки и используемая конфигурация набора данных.
`cy-train` без `ground_truth` по-прежнему принимает нативный `ultralytics.data`;
`skip_train=true` не запускает подготовку обучающего набора данных.

## Нативные параметры Ultralytics

Все команды работы с моделями используют верхнеуровневые группы `ultralytics` и
`ultralytics_predict`. Первая задаёт обучение детектора и его внутреннюю валидацию;
вторая — предсказания, включая `cy-val` и сравнение моделей. В файле предсказаний
активны все применимые параметры. Общие значения заданы видимыми ссылками, например
`imgsz: ${ultralytics.imgsz}`; ссылку можно заменить собственным значением.
Скрытого слияния двух секций при выполнении нет.

По умолчанию явно заданы `ultralytics.model: yolo11n.pt`, `imgsz: 960`, `compile: true`
и `nms: true`. Предсказания используют `conf: 0.001`, `batch: 1`, `rect: true`,
`save: false`; остальные общие параметры наследуются только через ссылки.
`compile` и `nms` включены по умолчанию по правилам проекта, а не библиотеки.
Нативные ограничения компиляции и возможный отказ с предупреждением сохраняются.

Скопируйте обычный YAML Ultralytics в `conf/ultralytics/default.yaml` без дополнительной
вложенности. В примерах сначала идут активные параметры детекции, затем закомментированные
параметры под управлением `cy` и параметры, неприменимые к стадии. Исходные
комментарии Ultralytics и порядок внутри разделов сохраняются. `task`, `mode`, `data`, `project`, `name`
закомментированы в обеих группах; `source` и `model` — также в группе предсказаний. Обучающие
`model`, `classes`, `fraction` доступны для редактирования; CSV-режим по-прежнему
переопределяет классы и долю данных. Это оформление примеров: все ключи доступны
при сборке конфигурации Hydra и через поддерживаемые переопределения, а YAML запуска
содержит фактические производные значения. Видеопотоки и выдача векторных представлений
не поддерживаются. Команды
выбирают группы через список `defaults` Hydra. Нативные ключи меняются обычным
переопределением без `+`:

```bash
uv run cy-train --config-dir=./conf --config-name=cy-train \
  ultralytics.data=data.yaml ultralytics.model=yolo11n.pt ultralytics.epochs=10
uv run cy --config-dir=./conf --config-name=cy ground_truth=ground_truth.csv \
  ultralytics.imgsz=1280 ultralytics_predict.batch=8
```

Общие значения задаются списком `defaults`, выбранным файлом группы и переопределениями Hydra.
Явные настройки `ultralytics_predict` имеют приоритет над общими, включая общие
переопределения командной строки. Явные `null` и значения, равные значениям по
умолчанию, сохраняют приоритет. Переопределение `ultralytics_predict.batch=8` меняет
настройку предсказаний поверх файла группы.

`cfg=training.yaml`, вложенные `train.ultralytics` / `predict.ultralytics` и нативные
поля внутри секции `inference` сравнения удалены. Значение `ultralytics.cfg`, отличное от `null`,
также запрещено.
Перенесите содержимое старого файла в группу; см. [миграцию](docs/migration-ultralytics-groups.md).

`device`, `batch`, `amp`, `compile` и аугментации остаются нативными параметрами.
Устройства независимы: обучение использует `ultralytics.device=null`, предсказания —
`ultralytics_predict.device=[-1]`. Переопределение устройства обучения не меняет устройство
предсказаний; для CPU задайте `ultralytics_predict.device=cpu`. Остальные общие ссылки
сохраняются. Автоматический подбор размера пакета при обучении (AutoBatch)
не меняет явно заданный размер пакета предсказаний.
Для отдельного предсказания укажите `weights` или `ultralytics_predict.model`;
архитектура обучения не служит запасной моделью. `imgsz: null` запрещён: размер
не берётся из файла весов. Старые конфигурации с неполными группами параметров
следует пересоздать через `cy-init-config`.
Устаревшие `half`, `int8`, `end2end` заменяются нативными `quantize` и `nms`.
Конвейер выбирает файл весов после обучения, изображения и выходные пути.
Противоречащие `run_dir` значения `ultralytics.project` / `ultralytics.name`
или явно конфликтующий файл весов для предсказаний вызывают ошибку.

Запрошенные настройки сохраняются отдельно в файлах `*_requested.yaml`. Ultralytics
сам приводит явно заданный размер 906 к шагу сети (например, 928 при шаге 32); исходное значение
не теряется. Целевой размер после нормализации модулем предсказаний записывается
отдельно от его аргументов.
При `rect: true` фактические тензоры отдельных пакетов могут быть меньше этой цели.
Эффективные настройки сохраняются в `ultralytics.yaml` и `ultralytics_predict.yaml`
соответствующих стадий, а для разных выборок и ролей сравнения — в отдельных YAML.
Они содержат фактический путь к файлу весов, источник данных (`source`) и режим (`mode`)
без служебных ключей Hydra; списки изображений сохраняются локально.
Эти файлы можно передавать непосредственно
Ultralytics при наличии исходных входов. Комментарии сохраняются локально. В ClearML
одна конфигурация `run` хранит настройки приложения, предсказаний, оценки и значимые изменения;
нативные параметры обучения находятся в `General`. Используемые конфигурации набора данных и
явного отчёта записываются отдельно. Копий конфигураций среди артефактов нет.

Перед загрузкой YAML/JSON в ClearML все активные значения интерполяций разрешаются:
можно ссылаться на другие поля файла, переменные окружения и текущую конфигурацию
команды после удалённых переопределений. Корневые поля файла имеют приоритет над
одноимёнными полями команды; лишние поля команды в загружаемый файл не добавляются.
Комментарии YAML сохраняются, включая примеры интерполяций в комментариях.
Исходный файл не меняется: выполнение получает разрешённые значения, а ClearML —
отдельную копию с удалёнными секретами. Неизвестные ссылки, циклы и ошибки резолверов
завершают команду и задачу с ошибкой. Вычисляемые имена ссылок вида `${${key}}`
отклоняются; вложенные аргументы резолверов `${oc.env:${variable}}` поддерживаются.
Локальные примеры `cy-init-config` сохраняют
интерполяции для редактирования.

## Оценка и сравнение

Пороги новой модели калибруются ровно один раз на `val`, а затем остаются
неизменными на выбранных выборках. В конвейере сравнение выполняется на `test`.
Отдельный `cy-compare` принимает переопределение `split` для другой выборки текущей разметки.
Обе модели проходят один и тот же набор выбранных изображений с одинаковыми настройками
предсказаний; сравнение не калибрует пороги повторно. Точные
пороги сохраняются один раз в CSV `metrics_best_confidences_val` со столбцами
`class_name,confidence` и полной точностью. Артефакты порогов прежнего формата поддерживаются.
Лучшие веса выбираются явно из нативной модели `best.pt`; для совместимости
также поддерживается старый артефакт с весами. Имена классов и архитектура читаются из файла весов.
В задаче сравнения сохраняются ссылки на источники и общие настройки предсказаний.

`cy-compare` принимает ссылки `baseline_model` и `candidate_model`, текущий
`ground_truth`, группы `ultralytics` и `ultralytics_predict`, `split=test` и выходной каталог. По умолчанию
базовая модель — последняя завершённая задача с тегом `prod`, кроме текущей задачи. Если
автоматический поиск ничего не находит, сравнение отмечается пропущенным. Некорректно
указанная явно задача или файл весов, а также отсутствие требуемых точных порогов —
ошибка.

Исторические панели показателей не сравниваются. Парные результаты выбранной текущей выборки
лежат в `comparison_dir` и одновременно служат источником статистики, технического и
бизнес-отчётов. Поэтому числа, исключённые классы и пороги во всех отчётах
описывают одну и ту же оценку.

## FiftyOne

`cy`, `cy-predict` и `cy-metrics` по умолчанию публикуют результат в локальный
постоянный набор данных FiftyOne. Зависимость устанавливается вместе с проектом.
Нужен доступный MongoDB: используйте встроенный сервер FiftyOne на поддерживаемой
системе либо задайте `FIFTYONE_DATABASE_URI`. Расположение локальной базы и блокировок
задаётся стандартной переменной `FIFTYONE_DATABASE_DIR`. Приложение не открывает
интерфейс просмотра и не копирует изображения: их исходные пути должны быть доступны
при просмотре.

Для отключения добавьте `fiftyone.enabled=false`. Этот режим не импортирует FiftyOne
и не обращается к его базе. При включённой публикации ошибка подключения или записи
завершает команду и задачу ClearML с ошибкой; уже созданные локальные результаты остаются.
`cy-val` и `cy-compare` не публикуют в FiftyOne.

Каждое изображение представлено одной записью с полями `image_name`, `split` и
`ground_truth`, включая фоновые изображения. Имя набора данных строится из
`fiftyone.dataset_prefix` (по умолчанию `clearml-yolo`), версии схемы и SHA-256
фактически используемого CSV разметки. При обучении это очищенный CSV.
Повторный запуск использует готовый импорт; пути изображений проверяются,
сами изображения повторно не читаются.
Изменение содержимого изображения при неизменном CSV не обнаруживается: входные
изображения считаются неизменяемыми. Для новой версии используйте новый CSV или префикс.

Результаты каждой задачи ClearML сохраняются в отдельных полях. `predictions_*`
содержит исходные предсказания; `matched_ground_truth_*` и `matched_predictions_*`
содержат фактически оценённые рамки. Атрибуты `dm_status`, `dm_index`, `dm_matches`
и `dm_ious` сохраняют статусы верных обнаружений (TP), ложных обнаружений (FP),
пропущенных объектов (FN) и исключённых из оценки рамок (`filtered`), индексы,
связи и долю пересечения относительно объединения рамок (IoU) из `digital-metrics`.
Повторное сопоставление разметки и предсказаний не запускается.
Поля `evaluated_*`, `tp_*`, `fp_*`, `fn_*` позволяют
отличить неоценённые изображения от изображений без ошибок. При импорте только CSV
предсказаний `predicted_*` равен `null` для изображений без рамок, если охват предсказаний
неизвестен. Пороговые значения и методика хранятся в `dataset.info["cy_runs"]`.

Точные имена полей и набора данных доступны в локальном `fiftyone_publication.json`;
ссылка на публикацию записывается в конфигурацию `run`. Например, открыть результат вручную:

```python
import json
import fiftyone as fo

with open("runs/my-run/fiftyone_publication.json", encoding="utf-8") as stream:
    receipt = json.load(stream)
dataset = fo.load_dataset(receipt["dataset_name"])
session = fo.launch_app(dataset)
session.wait()
```

JSON `metrics/evaluation_<split>.json` сохраняет переносимые результаты
сопоставления разметки и предсказаний,
а `fiftyone.enabled=false` позволяет заменить слой публикации без изменения вычислений.

`cy`, `cy-val` и `cy-metrics` по умолчанию оценивают `[train,val,test]`.
Явный `splits=[val,test]` сохраняет прежний выбор. Пороги калибруются один раз на `val`
и без изменений применяются ко всем выбранным выборкам. Отсутствующая запрошенная
выборка вызывает ошибку. Для каждой выборки публикуется одна книга
`metrics_evaluation_<split>.xlsx` только с таблицами `summary`, `per_class` и
`confusion_matrix`. Построчные сопоставления, пороги и методика публикуются рядом как
`metrics_evaluation_<split>_ground_truth_matches.csv`,
`metrics_evaluation_<split>_prediction_matches.csv`,
`metrics_evaluation_<split>_thresholds.csv` и
`metrics_evaluation_<split>_methodology.csv`. Каноническая таблица точных порогов
валидации по-прежнему называется `metrics_best_confidences_val.csv`.
В конвейере сравнение и бизнес-/технические отчёты
используют `test`; отдельное сравнение выбирает выборку через `split`, а отчёты читают её
из парного манифеста. `cy-val` формирует метрики без публикации в FiftyOne.

## ClearML и артефакты

При удалённом клонировании параметры обучения берутся из `General`, а пути
`project/name/save_dir` предыдущего запуска не переносятся: выходные каталоги
определяются текущей конфигурацией и идентичностью новой задачи.

При распределённом обучении (DDP) процесс с рангом 0 сохраняет события встроенных
обработчиков локально. Основной процесс читает их во время обучения через
установленную интеграцию ClearML: значение функции потерь, скорость обучения,
метрики валидации и время эпохи поступают после каждой эпохи. Финальная
публикация модели выполняется после проверки полноты событий. Рабочие процессы не создают
задачи и не публикуют данные. Для обычного обучения обработчики работают напрямую,
без повторной публикации.

Каждая команда исполнения создаёт ровно одну задачу ClearML; `cy-init-config`
только записывает локальные YAML. Вложенные стадии используют ту же задачу.
Все встроенные обработчики Ultralytics включены: разделы числовых показателей (`Scalars`),
графиков (`Plots`) и примеров изображений (`Debug Samples`) содержат результаты
обучения, валидации и предварительного просмотра изображений.
Рабочие процессы не создают задач и ничего не публикуют.
Обработчики включаются временно для основного процесса, их настройки восстанавливаются
после вызова; пользовательские настройки Ultralytics не перезаписываются.

`best.pt` публикуется ровно один раз как выходная модель ClearML (`Output Model`).
Та же запись получает название, архитектуру, классы, теги, описание, версии
и известные сведения о входах.
Сведения о происхождении заполняются только при наличии исходных данных;
модель не помечается готовой к промышленной эксплуатации.
Перед завершением проверяется загруженный файл весов, включая совпадение с локальными весами.

Скачиваемые артефакты — уникальные CSV разметки и предсказаний, точные пороги валидации,
CSV с сопоставлениями и методикой, книги оценки по выборкам, одна книга сравнения и
итоговые технический и бизнес-отчёты. Книги XLSX содержат только панели результатов
и таблицы метрик: в книге оценки это сводка, метрики классов и матрица ошибок, а в книге
сравнения — лист `Сравнение`. Исключённые из сравнения классы и методика сохраняются как
`compare_workbook_<split>_excluded.csv` и `compare_workbook_<split>_methodology.csv`.
Если автоматическая базовая модель не найдена, книга кандидата содержит только листы
`Classes` и `Summary`, а её пороги и причина пропуска записываются в
`compare_evaluation_candidate_<split>_thresholds.csv` и
`compare_evaluation_candidate_<split>_methodology.csv`.
Одинаковые таблицы не публикуются повторно. Пустая таблица предсказаний с заголовками
сохраняется как реальный результат. Сырые метрики, JSON-манифесты, NDJSON, архивы,
диагностические записи, дополнительные файлы весов и копии графиков остаются локально.
JSON-представления результатов и конфигурации, а также PNG-изображения не являются
табличными экспортами и сохраняют свои форматы. Подробности перехода приведены в
[миграции табличных экспортов](docs/migration-evaluation-csv.md).
Временные YAML вроде `0038.yaml`, `train_data_overrides.json` и другие копии настроек
не входят в артефакты. Настройки восстанавливаются из объектов конфигурации
(`Configuration Objects`) текущей задачи и её `General`;
ссылки на сравниваемые модели ведут к исходным задачам для
проверки происхождения. Сравнение загружает веса и пороги, но не импортирует автоматически
`General` или объекты конфигурации исходной задачи поверх своих настроек.
Общие настройки текущего сравнения применяются к обеим моделям, а точные
пороги загружаются из CSV валидации исходной модели.

Учётные данные не публикуются. Ошибка вычисления, регистрации модели, загрузки,
отправки накопленных данных библиотекой ClearML или прерывание завершают задачу
и команду ошибкой; локальные файлы остаются на месте.
Проверки обязательных публикаций выполняются внутри программы без отдельного артефакта-манифеста.

## Разработка

```bash
uv run pytest
uv run ruff check .
uv run mypy .
uv run lint-imports
```

Модульные тесты используют имитации внешних компонентов. Перечисленные проверки
не подтверждают реальное обучение, использование GPU или загрузку артефактов.
Для интеграционной проверки выполните пример из раздела «Быстрый старт»
на доступном наборе данных с отдельным проектом ClearML и явно выбранным устройством.
Проверьте результаты обучения, метрики, скачивание артефактов и файла `best.pt`
из завершённой задачи. Изменения конфигурации описаны в
[руководстве по переходу от 0.3.0 к текущему интерфейсу](docs/migration-030.md).

### Локальные версии и теги

Установите зависимости разработки и Git-хуки в каждом клоне:

```bash
git submodule update --init --recursive
uv sync --locked --dev
uv run --locked --no-sync python scripts/local_release.py --install-hooks
```

Команда установки подключает `pre-commit` и `post-commit`, не создавая выпуск.
Установщик сохраняет сторонний `post-commit`: если такой хук уже
есть, установка завершится с пояснением вместо перезаписи. Обычный `pre-commit install`
устанавливает только проверки перед коммитом; для автотегов нужна команда выше.
Сценарий выпуска использует `--all-files`, чтобы не скрывать незакоммиченные изменения.
После коммита в `master` Python Semantic Release анализирует сообщения
в формате Conventional Commits
после последнего достижимого тега `vX.Y.Z`. `fix:` и `perf:` повышают номер исправления
(`Z`), `feat:` — номер младшей версии (`Y`). Несовместимые изменения
(`!` или `BREAKING CHANGE:`) в серии `0.x` тоже повышают `Y`;
переход к `1.0` требует отдельного изменения правил выпуска.
Коммиты `docs:`, `chore:`, `test:` и другие нерелизные типы сами по себе версию
не повышают. Если предыдущая попытка была отложена, учитывается вся накопленная
история, а не только последний коммит.

Перед коммитом хук пересоздаёт [журнал изменений](CHANGELOG.md) из полной истории
Conventional Commits: изменения без выпуска версии попадают в раздел
«Ещё не выпущено» (`Unreleased`), записи служебных релизных коммитов исключаются.
Файл генерируется целиком; ручные правки
в нём будут заменены. Если содержимое изменилось, включая первое создание файла,
хук останавливает коммит: проверьте результат, добавьте `CHANGELOG.md` в индекс
и повторите коммит. Хук сам файлы не добавляет. Текущий коммит ещё отсутствует
в истории; его запись добавится при следующем обновлении либо при создании релиза.
Для ручного обновления используйте
`uv run --locked --no-sync python scripts/local_release.py --changelog`;
код 1 означает обновлённый файл, требующий проверки и добавления в индекс,
либо ошибку с пояснением; код 0 — отсутствие изменений.
Обновление работает и на именованных рабочих ветках без создания релиза;
при работе без выбранной ветки (отсоединённый `HEAD`) оно пропускается.

Хук релиза обновляет `pyproject.toml`, версию самого проекта в `uv.lock` и
раздел новой версии в `CHANGELOG.md`, выполняет обычные
проверки через отдельный коммит `chore(release): X.Y.Z` и создаёт на нём аннотированный
тег `vX.Y.Z`. Версии и источники зависимостей сохраняются. Проверки для исходного
и служебного коммитов выполняются отдельно; рекурсия отключается только для создания
релиза. Команды приложения и их девять точек входа не меняются.

На других ветках, при отсоединённом `HEAD`, во время перебазирования (`rebase`)
или переноса коммитов (`cherry-pick`) выпуск пропускается. Автоматический выпуск
также пропускается после изменения последнего коммита (`amend`), переноса коммита
или других операций перезаписи истории.
При изменённых отслеживаемых файлах или индексе он откладывается; незакоммиченные
изменения и остальные неотслеживаемые файлы сохраняются. Нужна полная история с исходным
тегом выпуска: хук не загружает её автоматически. Слияние простым продвижением ветки
не создаёт новый коммит и не вызывает `post-commit`;
при необходимости запустите команду вручную:

```bash
uv run --locked --no-sync python scripts/local_release.py
```

Ошибка `post-commit` не отменяет исходный коммит и может не изменить код завершения
`git commit`: прочитайте сообщение хука. Если проверка служебного коммита не прошла,
проверьте оставленные изменения, устраните причину, добавьте только `pyproject.toml`,
`uv.lock` и подготовленный `CHANGELOG.md` и завершите коммит с указанным
в сообщении номером версии:

```bash
git diff HEAD -- pyproject.toml uv.lock CHANGELOG.md
# После проверки изменений подставьте фактическую версию вместо X.Y.Z.
git add -- pyproject.toml uv.lock CHANGELOG.md
git commit -m "chore(release): X.Y.Z"
uv run --locked --no-sync python scripts/local_release.py
```

Если служебный коммит уже создан, но тег не записан, повторный запуск проверит этот
же коммит и создаст недостающий тег. Успешный повтор не создаёт ещё один коммит.
Во время незавершённой попытки хук сохраняет подготовленный журнал изменений.
Его SHA-256 записан в состоянии попытки: изменение подготовленного содержимого
блокирует создание тега. Старые попытки без контрольной суммы требуют ручного
разбора; они не получают тег автоматически по действующим правилам.
Существующие теги не заменяются; изменение истории после неудачной попытки требует
ручного разбора. Состояние попытки хранится в файле, путь к которому показывает
`git rev-parse --git-path clearml-yolo-release.json`. Удалять его следует только после
проверки и ручного завершения либо отмены именно этой попытки.

Одновременные выпуски из связанных рабочих деревьев Git блокируются общим каталогом
`clearml-yolo-release.lock` внутри `git rev-parse --git-common-dir`. После аварийного
завершения сначала проверьте `owner.json` и убедитесь, что указанный процесс больше
не работает; только затем удалите оставшуюся блокировку и повторите команду.

Автоматическая сборка пакетов в форматах wheel и sdist, непрерывная интеграция
и доставка (CI/CD), публикация и отправка в удалённый репозиторий отсутствуют.
Локальный тег обозначает версию, а не подтверждает реальное обучение или работу ClearML.
После проверки результата отправьте ветку и конкретный тег явно:

```bash
git push origin master
git push origin vX.Y.Z
```

Спецификация и сценарии проверки: [локальный выпуск версий](specs/003-semantic-release/spec.md).
